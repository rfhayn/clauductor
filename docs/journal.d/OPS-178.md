## What happened

The four lows OPS-104 left at its cap in `.claude/checks/name-residue.sh` (#346) are closed, each with a case shown failing first. Every setting that shapes `git grep`'s output is pinned on one call line (`scan`), and a "shaped" case sets every `grep.*` key `git help --config` lists against a repository at once, so a key a later git adds fails the check. Every candidate split of a line is read, not the longest tracked path, so a mirrored `x.go:1:<piece>` name hides no split. Tracked symlinks have their target blobs read. The fail-closed count is fed a line directly. Review then found the class the counter was guarding: a tracked file not in the working tree as itself (a sparse checkout's, a deleted one, one turned into a link) went unread with the scan passing clean, so now the scan fails on one. Each command residue runs is made to fail in turn, having written all its output, and must fail the scan.

## Decisions

- The issue's road to the counter (`grep.fullName=true` from a subdirectory) is closed by pinning `--no-full-name`, and no other road is known once every setting is pinned, so the case feeds `credit` a line itself. Pinning and an end-to-end road through the counter exclude each other.
- The pins are held to git's own list of its settings (`git help --config`), not to a list kept here: *enumerate the authority*.
- `--no-column` and `-F` pin settings that today change nothing the scan compares; they stay, and the comment says no case fails without them.
- A tracked file missing from the working tree fails the scan rather than being read from the index: `--cached` would miss an unstaged edit, and the gate runs only on a clean tree anyway.

## Surprises

- `git grep` quotes paths as `ls-files` does, from the top too, so a quoted name never reached the counter.
- The stubs first returned failure without running the command, and two exits (`ls-files`, `tr`) were then backstopped by later steps, so their cases proved nothing alone. A stub now runs the real command and then fails.
