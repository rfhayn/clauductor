## What happened

catch-up-guard's four under-reads (#280) and pr-merge-guard's renamed-repo read (#282) are closed. Each got a row that failed first. 16 `cug` rows in `checks/hooks.sh` failed on the unfixed hooks. In `checks/merge-guard.sh`, 6 of the 7 #282 guard rows failed there, and so did the refusal-message row; the 7th is an allow row, which passed as a foreign merge before and passes as this repo's now. All pass now. The reader reads short options as a cluster, git-core programs as git, an unquoted heredoc body's `$( … )`, and says ODD when it loses its place. The hook then counts the whole command as unknown, and counts a worktree on the main checkout's branch as the main checkout. pr-merge-guard asks GitHub (`gh api repos/<name> --jq .full_name`) before it treats a name that differs from origin's as another repository, and refuses when gh cannot say.

## Decisions

- Close the class where an authority exists, instead of adding a fifth spelling (PRAC-0010). Options follow git's parse-options (a cluster holding `u`). Programs follow git's dispatch (`git-<sub>`). The branch a worktree holds comes from its refs, not from the command that put it there. The paren case fails closed on any `)` that closes nothing, not on zsh's three known spellings. Refusing everything the reader cannot fully parse was rejected: the reader is not a shell, so that would refuse most commands.
- A renamed repo is policed, not just refused: a merge by the old name is this repo's merge, read by the name it gives, which GitHub redirects. A stale origin is covered the same way, because both names are resolved.

## Surprises

- macOS `/bin/sh` and bash 3.2 reject all three paren spellings as syntax errors. Only zsh, the Bash tool's shell here, runs them.
- `sub` is an awk builtin, so a function parameter named `sub` is a syntax error in BSD awk, and every reading then fell back to the raw one.
