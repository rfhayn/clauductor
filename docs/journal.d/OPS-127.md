## What happened

A new `project.conf` key, `APPROVAL_DELEGATED` (default `"0"` in `lib/conf.sh` and the template),
lets `change-approval.sh <id> --delegate "<owner>"` record
`**Approved:** <date> by Claude (delegated by <owner>) · design <hash>`. It refuses while the key is
off, and for a change whose records name any path in the new `.claude/approval-guarded.txt` (the
approval scripts, `project.conf`, hooks, settings, the review cap, budget enforcement,
build-change, CI workflows, `scripts/ci/`, `AGENTS.md`). The check mode, which `checks/changes.sh`
calls for every open change, re-tests both on every run, so turning the key off or later naming a
guarded path voids a delegated approval the way a design edit voids the owner's. An approval
written `by Claude` in any other form fails, and `--record Claude` is refused, so the delegated
form is the only way Claude's name reaches the line. Five self-test cases in `checks/changes.sh`
and the `--delegate` cases in `checks/change-tools.sh`; the negatives were run against the old
`change-approval.sh` first and failed there (the key off, a guarded path, a missing list, an empty
list, a plain `by Claude`).

## Decisions

- The guarded list is matched as literal substrings of the change's text (proposal, design, tasks,
  deltas), so `template/.claude/hooks/` is caught by `.claude/hooks/`. It is the authority the
  check iterates; an empty or missing list refuses every delegation rather than reading as
  "nothing guarded".
- `approval-guarded.txt` is a project file (scaffolded, the project adds to it), so the plugin
  packager places it in the scaffold (`plugin/build.go`, `place`).
- This repo's own key is NOT turned on in this PR: the permission classifier refused the edit that
  sets `APPROVAL_DELEGATED="1"` in `.claude/project.conf`, rightly, since it grants Claude the
  approval. The owner flips it by hand when they read the PR; OPS-128 puts the key to use.
