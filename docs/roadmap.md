# Roadmap

The program plan: phases, their order, and the change queue. The queue tables below are the
**authority** for what is next; every script reads them through one parser,
`.claude/roadmap-queue.sh` (`sh .claude/roadmap-queue.sh --check` validates this file).

## How this layers with the other records

```
docs/roadmap.md     ← THIS: phases, order, exit criteria, and the queue of rows
changes/<id>/       ← the ONE unit of work in flight: proposal, design, tasks (proposed just in time)
specs/              ← what the system does, per capability (promoted from a change when it merges)
docs/adr/           ← decisions with trade-offs, alongside
docs/prds/          ← the product requirements the rows come from
```

## How a row becomes a change

- **A row is the scoping unit until its turn.** Capturing an idea for later is a ROW, not a
  change directory. A row makes no design claims, so it cannot go stale the way a design can.
- **At most one change is proposed ahead** of the one being built (`docs/principles.md`, *Propose
  just in time*).
- **Every change ships its slice**: its `tasks.md` ends with a `Slice:` line.
- **Split before proposing**: a row that names more than about three write surfaces, or more than
  one screen, is several rows.
- **A team-queue issue is an input to a row, never a row itself**: the bot team's GitHub issues
  (`.claude/local/skills/session-start/team-queue.md`) feed rows, and only this file orders work.
  A `new-row` issue proposes a row; only the owner's approval makes it one, added here with the
  next free id and ` (team-queue #N)` (OPS-100). A free id is one neither this file nor
  `docs/roadmap-history.md` holds (OPS-147): `team-queue.sh --next-id` reads both.

## The grammar (the parser refuses anything else)

- `## Phase <N> — <title>` starts a phase. `### <section>` groups rows inside it.
- `**Owner:** <name>` under a phase heading names the phase's owner.
- A queue table has exactly this header: `| # | Change | Scope | Deps | Status |`.
- `#` is the row id, unique in the file, never changed. **Here it is the milestone id**
  (`PANEL-19`, `OPS-9`, `REL-1`, `ST-0`): commits and PR titles start with it (`PANEL-19:`).
- `Change` starts with the change id in backticks: a capability change (`` `panel-19-metrics` ``,
  branch `change/panel-19-metrics`), or `` `fix/<issue>-<slug>` `` / `` `ops/<name>` `` for the
  other lanes. Then a dash and what a user can now do.
- `Status` leads with one of: `⬜ queued` · `⬜ in flight (#N)` · `✅ merged (#N)` ·
  `❌ cancelled — <why>`. A cancelled change's `changes/<id>/` is removed with it (`git rm -r`;
  `changes/README.md`).
- The current phase is derived: the first phase with a queued or in-flight row.
- `Budget: $N` anywhere in a row is the change's cost appetite, `Budget: $N, soft` a soft one
  (the row is the authority for both; the proposal repeats them: OPS-91); `(due YYYY-MM-DD)`
  dates a row.

Rows that merged or were cancelled before the reset of 2026-10-27 (OPS-147), and sessions S4–S13,
are in `docs/roadmap-history.md`, word for word. Their ids stay taken:
`.claude/local/roadmap.d/history.sh` makes the queue UNKNOWN for every reader when a row here
reuses an id the history holds. The reset also renumbered the phases: a record written before it
(ADR-0011, `docs/plans/direction-shift.md`, the journal) uses the old numbers, which the history
keeps. Before OPS-8 this repo's branches were `feature/PREFIX-N-…`; rows from then keep those
names as their ids. Earlier history (M1–M7, LIFE-1) is in `docs/prds/` and the journal.

## Session plan

How the sessions run (the owner's decisions of 2026-10-21, as later rows changed them):
- **Short sessions.** A session is one row, or several rows that share context or files, listed
  together in *Rows*. Each starts fresh in its own worktree from the panel's lane templates, with
  no standing orchestrator lane (PANEL-55), reads only the repo (the row, `changes/<id>/`, the PR)
  and builds through merge.
- **Batched PRs, only where rows share files** (the owner, 2026-10-21). Rows that edit the same
  files may ship in one PR, titled with the first row's id (`OPS-89: … (with OPS-103)`), whose
  body says "Also closes OPS-103"; both rows flip to merged with that PR. *Rows* writes a batch
  `OPS-89 + OPS-103`, so Up next offers only the first (OPS-126). Otherwise each row has its own
  PR, even within one session. A row a session only proposes is written `OPS-109 (proposal)`,
  and its build may be planned in a later session as plain `OPS-109`.
- **The review cap, by risk.** A change takes its proposal's `**Risk:**` (low 2 rounds, normal 3,
  high 3; normal is what the owner called medium). An ops or fix row has no proposal, so it is
  normal unless its Change cell says `Risk: low` or `Risk: high`. Past the cap, what is left goes
  to KNOWN LIMITS with an issue or row that owns it, unless the owner says otherwise.
  `.claude/review-cap.sh <row>` reads it (the rounds are `REVIEW_CAPS` in `.claude/project.conf`):
  build-change's `maxRounds` defaults to it and merge-pr step 3 stops at it (OPS-108). A change
  row's `Risk:` is a floor too: Claude approves on delegation no proposal whose `**Risk:**` is
  below it, and none whose row says `Approval: owner` (`change-approval.sh`, OPS-131).
- **One row, one session, one PR; a daily close folds the records** (OPS-108). A row's session
  opens its PR as a draft at the start (`session-start/marker.sh`) and writes its records to
  `docs/journal.d/<row id>.md` in that PR, never to the journal, the insights log or a Status here.
  A daily close (or one every 3–4 rows) folds the fragments into one `## Session N`, N being the
  first plan session it covers, and sets each landed row's Status (`session-close/fold.sh`).
- **Owner decisions are taken ahead.** A row that needs one does not start without it, and while
  one row builds, the next one's proposal may be drafted.
- **One cloud lane beside the Mac session** where the plan has one (the owner's decision of
  2026-10-19, beside). It needs API credit (the owner queue); without it, its rows move onto the
  Mac, about 4–6 sessions later.
- **After each merge the owner** pulls the main checkout (`git pull --ff-only`); when the PR
  changed `framework/`, runs `./install.sh`, then `stridal panel install`; when it changed
  `.stridal/panel.json`, runs `stridal panel trust`. This applies only while catch-up is off
  for this repository on the owner's Mac: catch-up is on only when `stridal panel catch-up
  --project <main checkout>` exits 0 and prints `on`, and anything else (`off`, an older
  stridal, an error) counts as off. merge-pr's report names the step only then. With it on
  (OPS-118), the panel fast-forwards the checkout, trusts a config the owner's merge brought,
  rebuilds itself, and sends a notice for whatever it could not do. #164 stays open for its second item.
  This step goes with OPS-145, OPS-157 and OPS-202; OPS-202 removes this bullet.
- **The records** are kept by a close once a working day, or every 3–4 rows (OPS-108).

**From S19 on, the order is the engine re-plan of 2026-10-31** (OPS-182: ADR-0016 to ADR-0022
and the S19 deep dive): evidence before each decision, the floor before any port, the interfaces
before the ports, and each phase closed by its gate. Each multi-session row is drawn at its phase's
upper count. S14 to S18 ran in the order of the reset of 2026-10-27 (OPS-147); sessions S4–S18 are
in `docs/roadmap-history.md`.

Session numbers are estimates: a row that runs long moves the rest later and never reorders them.

header is not the queue header, so the queue parser skips it. In *The owner decides*, `ID: decision` names the decision a row needs before it starts. From S13 on, a cell names only what
stays the owner's (OPS-128): what `APPROVAL_DELEGATED` delegates to Claude (triage, scheduling and
splits, and a proposal's design and approval) is left out, unless the change touches a path
`.claude/lib/approval-guarded.txt` or `.claude/local/approval-guarded.txt` lists, the decision is
