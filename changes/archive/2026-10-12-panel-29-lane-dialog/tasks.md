## Decision log
- 2026-10-02 · group 1 · `GET /lanes/branch` takes `template`, `name` and an optional `issue`, and the server renders the branch (new `config.TemplateBranch`, sharing `RenderTemplate`'s branch rule). The issue is needed only when the branch pattern uses it. Alternative: the page renders the pattern and sends the branch. Why: one rendering, the same one Start uses, and the `fix` template's issue is in its prompt only, so the dialog can ask before an issue is typed.
- 2026-10-02 · group 1 · The 409 `branch-exists` reply carries the facts as top-level `branch`, `local`, `remote` and `worktree` (omitted when none), the same fields the GET answers with (`lanes.BranchFacts`). `remote` means "origin has it", and `local` says whether this clone has it too. Alternative: `remote` set only when origin alone has it, or a nested object. Why: the page reads one shape from both calls.
- 2026-10-02 · group 1 · "branch" for a branch that already has a worktree is refused with 409 `branch-exists` and that worktree, with the same sentence "new" gives in that case. The design's table doesn't cover this case. Alternative: run `git worktree add` and pass git's "already checked out" error through. Why: the change's rule is that an existing branch is never a raw git error, and the page's conflict path already moves the start to "existing" on a worktree fact.
- 2026-10-02 · group 1 (review round 1) · The `branch-exists` sentence offers only what the server would accept. It keeps the spec's opening, "A branch named X already exists", then adds one of three endings. With a worktree: ", in the worktree P. Start the lane on that worktree." For a template with no worktree: ". Start on the branch in a new worktree." For a plain lane with no worktree: ". Choose another name for the lane." The no-worktree endings add " on origin" when only origin has the branch. Alternative: the design's single sentence, "Start on its worktree, or on the branch in a new worktree." Why: a plain lane can't use "branch", and with no worktree the first suggestion is false.
- 2026-10-02 · group 1 (review round 1) · In "new" and "branch", the folder rule (409 `exists`) now runs after the fetch and the branch check, not before the registry intent. Alternative: keep it first and read the branch facts only when the folder exists. Why: the likeliest collision is an earlier "new" lane's worktree at exactly this lane's path, and that is the branch's worktree. The page needs `branch-exists` with the facts, not a bare `exists`. The refusal still leaves no record, because `fail` deletes it.
- 2026-10-02 · group 1 (review round 2) · The fetch before "new" and "branch" is now `git fetch --prune --quiet`. Alternative: keep the plain fetch, or check `git ls-remote` instead of the remote-tracking refs. Why: merge-pr deletes merged branches on origin, and a stale `refs/remotes/origin/<b>` would refuse a reused name as "already exists on origin" or offer a branch that is gone. Pruning touches only remote-tracking refs, never a local branch. Close's and Remove's own fetches (close.go, removewt.go) are left as they are, because they check merges, not branch existence.
- 2026-10-02 · group 1 (review round 2) · The D6 GET (`GET /lanes/branch`) does no fetch, so until a fetch prunes it, it can report `remote: true` for a branch origin has deleted. Start's own fetch prunes the ref, so a "branch" start of such a name then gets "No branch named X", and a "new" start succeeds. The GET is also off while panel.json is untrusted (409 `untrusted-config`, as at Start), so an untrusted branch pattern is never rendered or looked up.
- 2026-10-02 · group 1 (review round 3, owner's ruling) · `branchFacts` detects a worktree stopped mid-rebase or mid-bisect. Such a worktree is listed `detached`, but git still holds its branch. For each detached worktree it reads `rebase-merge/head-name`, `rebase-apply/head-name` (`refs/heads/<b>`) and `BISECT_START` (`<b>`) in the worktree's git dir (`git rev-parse --absolute-git-dir`). These are the files git itself reads to refuse the branch. Alternative: map `git worktree add`'s "already used by worktree" error to `branch-exists`. Why: the mapping fixes only "branch", and "new" (and the D6 GET) would still advise "Start on the branch in a new worktree". Reading the facts makes both modes honest with one mechanism and no parsing of git's error text. The extra command runs only when the branch exists locally and no worktree lists it.
- 2026-10-02 · group 1 (review round 3, kept) · (a) The folder refusal now waits for `fetch --prune` while holding `m.mu`, and "branch" holds the lock across a fetch. Stays: "new" held the lock across its fetch before this change, the fetch is bounded at 60 s, and a start is a rare, person-initiated action.
- 2026-10-02 · group 1 (review round 3, kept) · (b) The prune drops every stale remote-tracking ref, so a lane whose origin branch was deleted shows ↑0 ↓0. Stays: cosmetic, and it matches origin now, which is what `fetch.prune` gives anyone who sets it.
- 2026-10-02 · group 1 (review round 3, kept) · (c) D1 accepts the project root as "existing" when the root is on the template's branch. Stays: D1 means the worktree whose branch is the template's own, and the root is such a worktree then. The main checkout stays on main by convention (AGENTS.md, Branching), so the case is rare and the lane still runs on the right branch.
- 2026-10-02 · group 1 (review round 3, kept) · (d) A prunable worktree (its folder deleted) is still reported as the branch's worktree. Stays: git itself refuses that branch until `git worktree prune`, so the refusal is right and only its advice points at a missing folder. No queued change owns it (PANEL-30 covers Remove's wording, not prunable worktrees). Revisit if a person meets it.
- 2026-10-02 · group 1 (review round 3, kept) · (e) `config.TemplateBranch` duplicates `RenderTemplate`'s id and issue checks. Stays: the template lookup and the branch rule are already shared (`template`, `templateBranch`), and what remains is the issue check. A drift can only make the D6 GET disagree with Start, and Start's own branch check (the 409 fallback) catches that.
- 2026-10-02 · group 1 (review round 3, kept) · (f) A "branch" registry record reads as Corrupt to an older binary. Stays: it matters only on a rollback, and a corrupt record is shown and can be forgotten, never launched.
- 2026-10-02 · group 1 (review round 3, kept) · (g) A `--single-branch` clone never sees origin-only branches. Stays: unchanged behaviour. Its fetch refspec decides what it sees, and the panel follows the clone's own configuration.
- 2026-10-02 · group 1 (review round 4, owner's ruling) · A worktree found only through `holdsBranch` (detached by a stopped rebase or bisect) is a dead end, because D1, unchanged, refuses "existing" on a detached worktree. So the facts carry `busy: "rebase"|"bisect"` beside `worktree`, omitted otherwise, in the D6 GET and in the 409's top-level fields alike. "new", "branch" and the 409 then say "A branch named X is in the middle of a rebase (or bisect) in the worktree P. Finish or abort it there, then start the lane on that worktree." "existing" on that worktree is still refused (400), in the same sentence. Alternative: relax D1 for a held worktree, or point at the worktree as before. Why: D1 is the owner's, and advice that routes to a refused start is a dead end. Group 2: `planStart` treats `busy` as "show the sentence, offer no start".
- 2026-10-02 · group 1 (review round 4, owner's ruling) · Start's fetch is `git fetch --prune --quiet origin`. Alternative: fetch every remote. Why: `branchFacts` reads only `refs/remotes/origin`, so another remote's fetch is cost with no use.
- 2026-10-02 · group 1 (review round 4, kept) · Low 2: the folder check runs after `Registry.Begin`, so a crash mid-fetch leaves an orphan record whose Path is a pre-existing folder. Stays: nothing is lost. The orphan is shown, and Close removes a worktree only with consent and only a clean one.
- 2026-10-02 · group 1 (confirm round) · The `origin` argument of Start's fetch is untested, by choice. It is a cost choice: dropping it would fetch every remote, which is slower but correct, because `branchFacts` still reads only `refs/remotes/origin`. A regression breaks no behaviour, so a test would guard only speed.
- 2026-10-02 · group 1 · The refusals for "root" with a template and "branch" without one are in `Start`, before any git or tmux call, not in `StartLane`. A template's empty mode still means "new". Alternative: refuse them in `StartLane`. Why: `Start` is where `req.tpl` is known, so every caller gets the checks.
- 2026-10-02 · group 1 · "existing" with a template on a detached worktree counts as a D1 mismatch, and the message says "a detached HEAD". Why: no branch can be the template's branch.
- 2026-10-02 · group 1 · Branch existence comes from one `git for-each-ref` over `refs/heads/<b>` and `refs/remotes/origin/<b>`, and only exact names count. The remote is literally `origin`, as the design names it. Alternative: two `rev-parse --verify` calls. Why: one command. for-each-ref also matches the refs under a pattern, so only an exact name is taken.
- 2026-10-03 · group 2 · The page state's `approvals` is a map of change id to bool: true with an Approved line, false without, and a change with no proposal is absent. `signals.ReadChanges` is unchanged, so a change folder with no `proposal.md` is absent too. Alternative: a three-valued string with an explicit "none", which needs ReadChanges to report proposal-less folders to every metrics reader. Why: NEWLANE-4-S4's "no proposal" is a roadmap row not yet proposed, which has no folder at all, and absence already says it.
- 2026-10-03 · group 2 · The change id for the approval warning is the lane name (the build template's prompt is `/build-change {"change": "{name}"}`). A build template is one whose first prompt, after leading spaces, starts with `/build-change`; a prompt that only mentions it later is not one.
- 2026-10-03 · group 2 · The plan carries a `note` beside the design's six fields: the one line that says why it chose where the lane runs (D2's "explained in one line", NEWLANE-2-S3; the refusal's sentence for NEWLANE-2-S4). - 2026-10-03 · group 2 · `mode` is null when the plan selects nothing (no template: where it runs stays the person's and the lane type's), and a plan with no choice enabled means nothing can start. Group 3 disables Start when no choice is enabled. Alternative: a separate `blocked` field. Why: one fact, said once.
- 2026-10-03 · group 2 · With a template, `choices` enables only what the server would accept: "existing" only for the worktree on the template's branch (D1), "branch" only once the server's answer says the branch exists with no worktree, "new" only when neither is known, and "root" never. Before the GET answers, the plan uses the worktrees in the state and offers "new". Alternative: keep every radio enabled and let Start refuse. Why: an enabled choice that is always refused is the dead end the change removes.
- 2026-10-03 · group 2 · The "branch" and "conflict" intents also carry the dialog's `template`, `name` and `issue`, which the design's intent shapes leave implicit, and the plan ignores facts about a branch other than the one it renders (an answer that arrives after the name changed). - 2026-10-03 · group 2 · "New lane here" matches a branch against each pattern with `{name}` as `config.LaneIDRe` and any other placeholder as `[^/]+?`. A pattern with no `{name}` matches nothing. The plan returns no issue (not in its shape), so a matched issue template still asks for it. With no match the name is the folder's slug, as openStart names it today. `StartPlan.slug` is exported so group 3 can drop panel.js's copy.
- 2026-10-12 · group 3 (group 2's low) · The plan now carries `issue` beside `name`: the intent's issue, or for "New lane here" the one the branch fills in the pattern (`bug/{issue}-{name}`). Why: D6's "asks again only when the template or name changes" holds either way, and a name typed letter by letter would otherwise run `git for-each-ref` once per letter.
